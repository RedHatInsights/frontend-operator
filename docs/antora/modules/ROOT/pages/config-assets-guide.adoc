= Publishing Generated Configuration

The frontend operator can publish its generated base configuration to S3 using a valpop Job. Enable it on a `FrontendEnvironment`:

[source,yaml]
----
spec:
  enableConfigAssets: true
  valpopImage: quay.io/redhat-services-prod/hcc-platex-services-tenant/valpop:latest
----

Pin `valpopImage` to a tested release or digest for deployment. The image must provide `valpop populate`, `--cache-max-age`, `--valpop-image`, and `--secure`, plus `/bin/sh` and `cp` for staging the files.

This is opt-in and independent of `enablePushCache`, `Frontend.spec.pushCacheEnabled`, and `disableContainerDeployments`. It can run while frontend containers are disabled. A Frontend must still reference the environment to trigger reconciliation.

== Files and storage

The publisher uploads the following files when generated in the environment's base ConfigMap:

* `fed-modules.json` (required): the operator-generated module registry.
* `bundles.json`
* `search-index.json`
* `api-specs.json`
* `service-tiles.json`
* `sso-config.json`
* `exports.json`

[cols="1,2,2",options="header"]
|===
| File | Contract | Producer and consumer
| Per-application `fed-mods.json`
| Module-federation build manifest describing the application's loadable assets. Its URL is the registry entry's `manifestLocation`.
| Produced by the application's build tooling; consumed by the frontend module loader.
| Aggregate `fed-modules.json`
| Object keyed by application name, with `FedModule` entries (`manifestLocation`, `modules`, `config`, and other CRD-defined fields).
| Generated by FEO from Frontend resources. Used by Chrome's operator-generated configuration path and as input to the Chrome service's configuration processing. This publisher copies its bytes to `data/config/fed-modules.json`.
| Processed `fed-modules-generated.json`
| Application registry after merging the FEO entries with legacy static configuration; FEO entries override matching application keys.
| Produced by `chrome-service-backend` configuration processing and consumed by Chrome through `/api/chrome-service/v1/static/fed-modules-generated.json`. It is not generated by this publisher.
|===

The publisher does not merge legacy configuration or change consumer URLs. Enabling it preserves the existing Chrome mount at `/srv/dist/operator-generated/fed-modules.json` and its public `/apps/chrome/operator-generated/fed-modules.json` path while Chrome deployments remain enabled. Turning on `disableContainerDeployments` removes those deployments and is a separate rollout decision: any consumer still using the legacy path needs routing or consumer changes first. The object-storage prefix is not an alias for that public URL.

The Caddyfile, widget/layout ConfigMaps, locale messages, and `locales.json` are excluded. The locale manifest is excluded because its referenced messages are not published by this Job. Changes only to excluded files do not trigger an upload.

Valpop uses prefix `config`, placing files under `data/config/<filename>` in the configured bucket. JSON objects receive `Cache-Control: public, max-age=60`. Bucket access policy, CDN routing, and switching consumers to these URLs are configured separately. Environments that require isolation must use separate buckets; the `config` prefix is shared within a bucket.

Credentials and destination use the existing push cache configuration, including Secret references. The Job contains `secretKeyRef` environment variables, not literal credentials. For local development, the operator can read the `env-<namespace>-minio` Secret used by existing push cache tests.

== Upload lifecycle

There is one config upload Job per environment and namespace. After generated ConfigMaps have been saved, the operator creates an immutable snapshot containing exactly the selected files. An init container copies the projected files into an `emptyDir`, so valpop reads regular files rather than Kubernetes ConfigMap symlinks.

The upload identity includes the filenames and contents, destination, cache policy, and refresh timestamp. A configuration change therefore uploads even when the frontend and valpop images stay the same. An unchanged completed Job is retained without another upload. Changing `valpopImage` replaces the Job, although valpop can still skip uploading unchanged content.

The operator waits for foreground deletion of the previous Job and its pods before replacing the snapshot. Failed Jobs are reported through the existing Frontend reconciliation error and retried. Publication runs after generated resources have been applied and obsolete Frontend resources have been pruned, so upload errors cannot block that cleanup. Each Job has a five-minute deadline and a backoff limit of three. Pending Jobs are checked every ten seconds.

To force another upload with identical content, change the refresh timestamp:

[source,yaml]
----
spec:
  deployCutoffTimestampConfigAssets: "2026-11-11T12:00:00Z"
----

The timestamp is a refresh token: changing it forces a new identity, rather than comparing it to the Job's creation date. Admission requires an RFC3339 timestamp with a timezone (`Z` or a numeric offset such as `+01:00`).

Setting `enableConfigAssets: false` removes the upload Job and snapshot on reconciliation. It does not remove uploaded S3 objects. Files removed from the generated inventory follow valpop's retention/cleanup behavior (`minAssetRecords`, default 3, and a 48-hour retention timeout); they are not guaranteed to disappear immediately. Uploads overwrite individual object keys, so this mechanism does not provide an atomic switch of all configuration files or a transactional rollback.

The operator also removes the Job and snapshot when the last Frontend in that namespace is deleted or moves to another environment. Shared resources remain while another Frontend in the same namespace references the environment. Frontend finalization waits for the uploader's foreground deletion before releasing its snapshot.

== Local verification

Run the dedicated integration test described in `tests/integration/README.md` against minikube with FEO running locally. It reads the objects back over HTTP, checks cache headers and excluded files, and changes only the registry configuration while preserving both images. The standard API-server-only KUTTL suite cannot run upload pods.
